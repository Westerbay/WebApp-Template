## Backend maintenance

The default pnpm commands target `apps/api-nestjs` (`@workspace/api`). Rust lives
in `apps/api-rust`; its validation entry points are:

```sh
node scripts/template-rust/check-assets.mjs
sh scripts/template-rust/check.sh
sh scripts/template-rust/runtime-check.sh
node scripts/template-rust/frontend-check.mjs
pnpm clean:rust
pnpm api:generate:rust
pnpm api:check:rust
```

`pnpm clean:rust` removes compiled Rust artifacts from `apps/api-rust/target`.
The next Rust build recompiles them; source files, Cargo downloads and database
volumes are preserved.

Run `pnpm template:check` to generate and inspect all six backend/locale archives.
Each generated project contains its selected backend under `apps/api`.
See the [Rust guide](../apps/api-rust/README.md) for contract generation and runtime details.

## Template releases

The [release workflow](../.github/workflows/template-release.yml) validates all six
ZIPs before publication. It reuses the tag's published release, or resumes its sole
draft, before creating a new draft. Uploads and publication target that release's
ID. A retry skips identical assets and refuses to overwrite different or incomplete
files; resolve those conflicts before retrying. Existing duplicate drafts are not
deleted automatically. Run `node --test scripts/test/template-release.test.mjs`
to check publication paths without contacting GitHub.

## Start locally

Use Node.js 24 and pnpm 12. Copy `.env.example` to a local `.env`; never commit
or share the real file.

```bash
pnpm install --frozen-lockfile
pnpm dev:infra
pnpm db:migrate
pnpm dev
```

The default ports are web 3000, API 3001 and PostgreSQL 5433. `pnpm run setup`
starts infrastructure and applies guarded migrations; it does not seed.
`pnpm dev:down` stops services without deleting the database volume.

`pnpm dev` generates translations before starting Vite, the Nest API and the
translation watcher. Generation failure prevents these consumers from starting;
subsequent catalog edits are regenerated by the watcher.
Use pnpm as the common entry point for development commands. To reclaim unused
packages in pnpm's shared store, run `pnpm store prune`; this does not clean builds.

The standard `compose.yml` stays at the root; optional and test stacks live in
`infra/compose/`. Infrastructure scripts live in `scripts/infra/`; use the root
pnpm commands as their entry points. Keep `.mjs` for structured files, subprocess
orchestration and resource cleanup; Bash suits short shell-specific CI steps.
`pnpm tooling:test` checks the optional stack launcher without Docker (its POSIX
executable stub is skipped on Windows). Integration, E2E and observability
suites require Docker and clean only their own temporary resources.

PostgreSQL and optional Grafana use maintained local image recipes rather than
published custom tags. Their pinned sources, rebuild procedure and maintenance
constraints are documented with the [PostgreSQL recipe](../infra/images/postgres/README.md)
and [Grafana recipe](../infra/images/grafana/README.md). The first start builds
them; later starts reuse the local images. Rebuild explicitly after recipe updates.
Grafana bundles only the Loki and Prometheus integrations used by this template.

## Languages and public paths

Edit `packages/i18n/messages/<locale>.json` for UI and email copy and
`packages/i18n/routing.json` for public paths. Supported languages and the
default are in `packages/i18n/project.inlang/settings.json`. Internal routes
and API paths stay English. Rebuild generated types after changing catalogs:

```bash
pnpm --filter @workspace/i18n build
```

## Checks and generated API

```bash
pnpm check
pnpm format:check
pnpm lint
pnpm typecheck
pnpm test
pnpm build
pnpm docs:check
pnpm project:check
pnpm boundaries:check
pnpm boundaries:test
pnpm test:integration
pnpm test:e2e
```

E2E writes mobile screenshots and JUnit results under `output/playwright/<locale>/`.
A browser failure also saves `auth-failure.png` when the page is available. Failed
CI E2E runs upload available diagnostics as `e2e-diagnostics`, retained for seven
days; download them from the workflow run's artifacts.

Fast checks need no database. Integration and E2E use owned temporary
infrastructure and require Docker; install their browser with
`pnpm --filter @workspace/api exec playwright install chromium`.
`docs:check` validates documentation links; `project:check` checks project
boundaries and configuration. Its `boundaries:check` stage uses dependency-cruiser
to resolve imports against workspace exports and web TypeScript aliases. Build
workspace packages first so generated exports are available; `pnpm check` does
this through typecheck. The tooling-only `scripts/tsconfig.boundaries.json`
inherits web aliases and supplies the resolver's required base URL. Unresolved
source imports fail the check, except Vite CSS URL assets. Run `boundaries:test`
to exercise rejected and allowed dependencies in isolated fixtures.
After changing Nest controllers or DTOs, run
`pnpm api:generate` and include the generated API schema and web client types.
`pnpm api:check` verifies drift without a database or SMTP connection.

The frontend validates `/api/me` and `/api/users` before caching their responses.
`apps/web/src/lib/api/contracts.ts` reuses the shared Nest Zod schemas directly;
Nest projects do not install Orval or regenerate these schemas through OpenAPI.

## Security and dependency updates

The [CI guide](CI.md) describes event planning, validation reuse and required
statuses. [Security CI](../.github/workflows/security.yml) is called once by the
entry workflow for PRs, direct main pushes, manual runs and weekly security
refreshes. It scans secrets, JavaScript and Rust dependencies, and a matrix of
unique infrastructure images. HIGH/CRITICAL vulnerabilities, including unfixed
findings, and scanner service errors fail the checks. No real environment file
or database is needed. Require `CI checks` and `Security checks` in branch rules
to enforce these results.

[Renovate configuration](../renovate.json) prepares weekly update PRs for workspace
dependencies, Compose/Dockerfile images and GitHub Actions. Install the
[Renovate GitHub App](https://github.com/apps/renovate) on each repository using the
template to activate updates. Compatible minor/patch updates are grouped; major
updates stay separate and merging remains manual. pnpm updates remain manual
because CI and project validation also pin its version. Keep image references in
JavaScript test harnesses aligned when reviewing Compose image updates. Renovate
does not update arbitrary image strings embedded in scripts.

The security workflow and Renovate configuration are included in generated projects.
To reproduce the dependency audit locally, run `pnpm -r audit --audit-level high`
after installing dependencies. Image scanning requires access to public registries
and Trivy's vulnerability database.

The shared UI imports the extracted shadcn 4.21.0 utilities from
`packages/ui/src/styles/shadcn.css`, retaining their MIT notice. The shadcn CLI is
not an installed dependency; use `pnpm dlx shadcn@latest` when adding components.
Upstream changes to `shadcn/tailwind.css` must be reviewed and copied explicitly.

## Local data and email

Migration and seed commands refuse staging, production and remote or
unverified databases. Enable fixture mode locally before running:

```bash
pnpm db:seed -- --scenario auth
pnpm db:seed -- --all
pnpm db:seed -- --scenario auth --clean
```

The auth scenario supplies two reference accounts and 60 sample profiles.
Fixture configuration lives in `apps/api-nestjs/src/seeds/auth/fixtures.config.ts`.
Clean fixtures with the old configuration before changing their IDs or count;
cleanup recognizes only its own records. The initial migration is an auth-only
baseline and does not apply to databases from an older migration history.

Development email goes to Mailpit on SMTP 1025, with its UI at
`http://localhost:8025`. Production SMTP needs explicit credentials, sender
and TLS. Staging SMTP is opt-in and uses an exact recipient allowlist. New
passwords are checked with Have I Been Pwned only in staging/production; allow
outbound HTTPS to `api.pwnedpasswords.com` there. Development/tests stay
offline.

## Reusing cursor pagination

Define the response and bounded query in `packages/contracts`, use a unique
stable order and `limit + 1` rows with `createCursorPage` in the API, then
regenerate OpenAPI. In the web app, use `useCursorInfiniteQuery`, include page
size and filters in the query key, and forward the abort signal. The users
feature is the working example.

## Observability and health

Development logs are readable; staging/production require JSON stdout.
Responses carry `x-request-id`. HTTP logs omit headers, bodies, cookies,
tokens and personal data. Liveness does not contact dependencies; readiness
checks PostgreSQL and enabled Valkey. Configure proxy trust only for a verified
proxy chain.

The optional observability stack provides four Grafana dashboards, Loki logs,
Prometheus metrics, a readiness probe and starter alert rules:

```bash
pnpm logs:up
pnpm dev:logs
pnpm logs:check
pnpm logs:test
pnpm logs:down
```

See [OBSERVABILITY.md](OBSERVABILITY.md) for a self-contained preview, metrics
network access, dashboard scope, production integration and alert runbooks.
Alloy embeds PostgreSQL and Valkey exporters independently of the API.
PostgreSQL SQL statistics are enabled by default in the observability stack. Setup and
diagnostic procedures are documented in
[POSTGRESQL-PERFORMANCE.md](POSTGRESQL-PERFORMANCE.md).

## Optional shared quotas

The base API needs no Valkey. Start its independent local service, then enable
the API with `VALKEY_ENABLED=true` and a loopback `VALKEY_URL`. Keep
`VALKEY_NAMESPACE` distinct per application/environment and identical across
replicas. The local service is ephemeral and has no authentication; deployed
Valkey needs platform-managed access and availability.

```bash
pnpm valkey:up
pnpm valkey:test
pnpm valkey:down
```

Enabled Valkey is required at startup and for readiness. Failed quota checks
return 503. Better Auth rate limits and sessions remain in PostgreSQL.

## Git worktrees

```bash
pnpm worktree:create
pnpm worktree:remove
pnpm worktree:check
```

Create and remove accept a branch name interactively or as an argument. Paths
live under the ignored `.worktree/` directory of the main checkout. Creation
checks out an existing local branch or starts a new one at main checkout HEAD.
Removal must run outside the target worktree and preserves its branch; Git
refuses dirty or locked worktrees. Dependencies and local env files are not
copied into a new checkout.
